# QAZAQTEST — сайт поставщика лабораторного оборудования

React 19 + Vite + Tailwind CSS 4. Оборудование для дорожных, строительных и
материаловедческих лабораторий Казахстана: каталог на 135 позиций в 12 разделах
и 27 подразделах, страницы товаров, поиск по всему каталогу, мега-меню,
карусель брендов, форма заявки.

## Команды

```bash
npm install               # зависимости
npm run dev               # дев-сервер (http://localhost:5173)
npm run catalog:import    # импорт выгрузки WooCommerce (CSV)
npm run catalog:build     # пересобрать каталог из выгрузки
npm run images:download   # скачать фото товаров к себе (см. ниже)
npm run images:optimize   # сжать скачанные фото под витрину
npm run build             # прод-сборка в dist/
npm run preview           # предпросмотр прод-сборки
npm run sitemap           # пересобрать sitemap.xml и robots.txt
npm run lint              # ESLint
```

## Каталог

Карточки собираются конвейером, а не правятся руками:

```
src/data/catalog.generated.json   выгрузка из Excel (источник, не редактируется)
        ↓  scripts/normalize_catalog.mjs  +  src/data/catalog.overrides.json
src/data/catalog.json             витрина, её импортирует сайт
```

`npm run catalog:build` перезаписывает `catalog.json` целиком, поэтому правки
вносятся одним из двух способов:

- **системная проблема** (разбор характеристик, чистка текста, бренды) — правило
  в `scripts/normalize_catalog.mjs`;
- **одна позиция** (уточнили название или цену) — запись в
  `src/data/catalog.overrides.json`, ключ — идентификатор записи в
  WooCommerce: `{ "wp-1009": { "title": "…" } }`.

Что делает нормализация: собирает аннотацию из целых предложений вместо
обрезанных на «…» строк выгрузки, разбирает характеристики в пары
«параметр — значение», отделяет списки от прозы, вытаскивает код модели и бренд,
дописывает код модели к повторяющимся названиям (в выгрузке было девять
одинаковых «Тестеров стабильности Маршалла»), убирает артефакты Excel и
переводит цену в число.

## Фото товаров

Снимки лежат в `public/products/` под именем `wp-<id записи в WooCommerce>` —
тем же ключом, что и правки карточек, поэтому переимпорт выгрузки их не
перемешивает. Путь к файлу прописан в `catalog.overrides.json`. Позиция без
снимка не ломает вёрстку: `ProductImage` рисует заглушку с кодом модели.

Сейчас снимки есть у 134 позиций из 135.

Скачиваются они из медиатеки магазина и сжимаются под витрину:

```bash
npm run images:download   # скачает в public/products/ и пропишет пути в overrides
npm run images:optimize   # WebP, не длиннее 1000 px по большей стороне
npm run catalog:build     # подтянет их в витрину
```

Сжатие обязательно: медиатека отдаёт файлы как есть, до 2565 px и 3,9 МБ на
снимок, тогда как карточка выводит их в контейнере около 300 px. На текущем
наборе это 16,1 МБ против 2,1 МБ — при неразличимой глазом разнице.

## Цены

**Цена на сайте — постоянная величина, а не пересчёт по курсу.** Компания
держит фиксированные цены, поэтому в витрине лежит готовое число в тенге
(`priceKzt`), и никакой арифметики при отрисовке не происходит: правка
коэффициента не может сдвинуть все ценники разом.

Цена конкретной позиции задаётся в `catalog.overrides.json`:

```json
{ "wp-1040": { "priceKzt": 4218000 } }
```

Пересборка каталога её не трогает. Рублёвая цена из выгрузки сохраняется в
`priceRub` как справочная, но на витрине не используется.

Для новых позиций, у которых своей цены ещё нет, `normalize_catalog.mjs`
подставляет ориентир по курсу `RUB_TO_KZT_SEED` — это отправная точка для
менеджера, а не действующая цена. Позиция без цены выводится как
«Цена по запросу»; придумывать цену нельзя.

## Поиск по каталогу

Иконка «лупа» в шапке (и на десктопе, и на мобильном) открывает панель поиска с
живыми подсказками; Enter или «Показать все результаты» ведут на `/search?q=…`
с фасетами по категории и бренду и сортировкой по цене. Внутри категории
остаётся свой быстрый фильтр, а если он ничего не нашёл — появляется ссылка
«Искать по всему каталогу».

Логика в `src/lib/search.js`:

- индекс строится один раз при загрузке модуля по витрине `catalog.json`;
- поля взвешены (название и модель важнее описания), токены запроса
  объединяются по И;
- нормализация: регистр, `ё → е`, знаки-разделители, поэтому `HYJB-30`
  и `hyjb 30` дают один результат;
- грубый стемминг под русские окончания как запасной вариант с пониженным
  весом: «ситовой» находит «ситового»;
- короткие слова (< 5 символов) ищутся только с начала слова, иначе «печи»
  находилось внутри «обеспечивает».

## Тексты карточек

Разбор дефектов выгрузки, единая структура карточки и редполитика — в
`docs/catalog-copy-audit.md`. Механические правила (единицы, словарь имён
параметров, разведение одинаковых названий, разбор слитых характеристик)
живут в `scripts/normalize_catalog.mjs` и применяются при
`npm run catalog:build`. Написанные тексты — в `catalog.overrides.json`.

`npm run catalog:lint` проверяет аннотации по редполитике: длина, обрывы,
дублирование описания, оценочная лексика, единицы по ГОСТ 8.417. Режим
`node scripts/check_copy.mjs --facts` выдаёт фактолист по проблемным
позициям — из него пишется текст.

## Адреса и индексация

Роутер — `BrowserRouter`, адреса обычные: `/catalog/asphalt/tester-…-lwd-5b`.
До этого был `HashRouter`, и весь сайт для поисковика выглядел одной страницей
`qazaqtest.kz/`, а `canonical` со всех карточек указывал на главную.

**Хостинг обязан отдавать `index.html` на любой путь**, иначе прямой заход по
ссылке на карточку вернёт 404. Правила уже лежат в репозитории:

| Площадка | Файл |
| --- | --- |
| Netlify | `public/_redirects` |
| Vercel | `vercel.json` |
| nginx (Cloudzy и любой VPS) | `deploy/nginx.conf.example` — готовый конфиг |
| GitHub Pages | fallback не поддерживается штатно, нужен обходной путь через `404.html` |

`usePageMeta` на каждой странице ставит заголовок, описание, `canonical` и
`og:url` по текущему адресу. Страницы поиска и 404 закрыты `noindex`.

`npm run build` перед сборкой вызывает `npm run sitemap`: карта на 154 адреса
(12 разделов и 135 карточек) собирается из `catalog.json`, поэтому не разъезжается
с каталогом.

Домен задаётся константой `SITE_ORIGIN` в `src/constants.js` и в
`scripts/generate_sitemap.mjs`.

## Палитра и контраст

Акцент разведён на два токена в `src/index.css`, потому что фирменный
`#D86350` не набирал 4,5:1 ни на одном фоне сайта (проверка axe-core давала
138 нарушений):

| Токен | Значение | Где | Контраст |
| --- | --- | --- | ---: |
| `--accent` | `#C2513F` | заливки кнопок и чипов с белым текстом | 4,62:1 |
| `--accent-text` | `#A13724` | надзаголовки, ссылки на светлом | 6,80:1 на белом |
| `--muted-text` | `#4A5A72` | подписи полей, копирайт | 4,98:1 на мятном |
| `--coral` | `#D86350` | логотип и декор без текста | — |

Осталось одно замечание axe — «TEST» в логотипе на тёмной шапке (2,52:1).
Это логотип, а WCAG 1.4.3 логотипы от требований к контрасту освобождает.

**Важно про `@layer`.** Базовые стили в `index.css` лежат в `@layer base`. Без
слоя они оказываются вне каскада Tailwind и перебивают утилиты: правило
`a { color: inherit }` гасило любой класс цвета на ссылках — телефон в подвале
и хлебные крошки рендерились унаследованным серым вместо акцентного цвета.
Новые базовые правила добавлять только внутрь этого слоя.

## Пополнение каталога из WooCommerce

Каталог rutestin.com — тот же поставщик, российский рынок — ведётся в
WooCommerce, и позиции берутся оттуда штатным экспортом, а не парсингом
страниц.

**Как выгрузить.** В админке: *Товары → Все товары → Экспорт*. Отметить «Все
колонки» и «Все категории», получить CSV. Заголовки в файле локализованы под
язык сайта — импортёр понимает и русские, и английские.

```bash
node scripts/import_woocommerce_csv.mjs data/wc-products.csv --dry-run  # посмотреть, что получится
node scripts/import_woocommerce_csv.mjs data/wc-products.csv            # → catalog.generated.json
npm run catalog:build                                                   # → catalog.json
npm run catalog:lint                                                    # проверить тексты
```

`--dry-run` разбирает файл и печатает отчёт, ничего не записывая. С него стоит
начинать: если сопоставление категорий не подошло, витрина не будет затёрта
огрызком каталога.

**Что откуда берётся.**

| Поле витрины | Источник в выгрузке |
| --- | --- |
| раздел | дерево «Категории», см. `CATEGORY_BY_NAME` |
| подраздел (`group`) | последний уровень того же дерева: «Асфальтобетон > Уплотнители» |
| `brand` | колонка «Бренды» (значение «Китай» — это страна, а не бренд, и отбрасывается) |
| `model` | «Модель: LHRS-6» в конце названия |
| `specs`, `features`, проза | разметка описания: подзаголовки «Характеристики товара», «Главная особенность», «Описание товара» |
| `tags` | колонки атрибутов — магазин держит там синонимы названия, они работают как поисковые теги |
| цена | «Базовая цена»; ноль означает «цена по запросу», а не 0 ₽ |

Описания в магазине свёрстаны единообразно: жирный подзаголовок, под ним
список или строки-абзацы. Импортёр разбирает их обратно в поля, поэтому
характеристики и особенности не сваливаются в сплошной текст.

Импортёр пропускает черновики и вариации товара. Позицию, чья категория не
сопоставлена ни одному разделу витрины, он **не выбрасывает**, а помечает
`categoryId: null` и печатает списком: раздел ей можно назначить правкой по
`wpId`. Если раздела так и нет, `npm run catalog:build` отсеет её — тоже с
сообщением, а не молча.

**Фотографии.** Снимки в выгрузке ссылаются на медиатеку rutestin.com. Чтобы
казахстанский сайт не зависел от российского хостинга:

```bash
npm run images:download   # скачает в public/products/ и пропишет пути
npm run images:optimize   # сожмёт под витрину
npm run catalog:build
```

Оба скрипта безопасно перезапускать: загрузчик пропускает уже скачанное, а
оптимизатор — уже сжатое, поэтому WebP не пережимается по кругу с потерей
качества на каждом проходе.

## Отправка заявок

Форма отправляет JSON `{ name, phone, topic, page, submittedAt }` на адрес из
`VITE_LEAD_ENDPOINT`. Переменная читается **во время сборки** — поменяли,
пересоберите сайт.

Если переменная не задана или запрос не прошёл, заявка не теряется молча: на
экране появляется «Заявка не ушла автоматически» и кнопка «Продублировать в
WhatsApp» (номер — `WHATSAPP_PHONE` в `src/constants.js`). Показывать
«Заявка принята», когда её никто не получил, нельзя — человек будет ждать
звонка, которого не будет.

**Обработчик под VPS** — `server/lead-service.mjs`: HTTP-сервис без единой
зависимости, работает на голом Node 20+. Он пишет заявку в журнал на диск и
шлёт уведомление в Telegram.

Журнал пишется первым и не зависит от Telegram: уведомление может не уйти, а
заявка при этом останется на диске, и клиенту можно перезвонить.

```bash
LEAD_TG_BOT_TOKEN=… LEAD_TG_CHAT_ID=… node server/lead-service.mjs
curl -s localhost:8081/health     # {"ok":true,"telegram":true}
```

Telegram, а не почта, потому что письма со свежего VPS почти всегда уходят в
спам: у нового IP нет репутации, нужны SPF, DKIM и прогрев домена. Telegram
работает сразу и приходит на телефон.

Что сервис умеет помимо приёма: два раздельных ограничения частоты (поток
обращений и число принятых заявок — чтобы опечатавшийся человек не расходовал
лимит наравне со спам-ботом), проверка `Origin`, потолок на размер тела,
отказ при недоступном журнале.

Разворачивание целиком — `deploy/DEPLOY.md`: nginx, systemd, TLS, проверка.

## Что заполнить перед запуском

- **`VITE_LEAD_ENDPOINT`** — пока не задан, заявка никуда не уходит. Форма в
  этом случае честно показывает «Заявка не ушла автоматически» и предлагает
  WhatsApp: обещать звонок по заявке, которой никто не получил, нельзя.
- Домен `SITE_ORIGIN` в `src/constants.js` и `scripts/generate_sitemap.mjs`,
  если он отличается от qazaqtest.kz.
- Правило SPA-fallback на хостинге — без него глубокие ссылки вернут 404.
- Ветка по умолчанию в настройках репозитория — должна быть `main`.
